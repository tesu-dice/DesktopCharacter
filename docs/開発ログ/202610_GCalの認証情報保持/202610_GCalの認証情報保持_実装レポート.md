## 2. 確認したこと（この環境で行った範囲）
- `.venv` の Python 3.9.13 で、変更した4ファイルの構文を確認（`py_compile`）。
- モックを使った確認スクリプト（42項目、すべてOK）。ネットワーク・ブラウザは使っていない。
  - 権限OFF・「毎回承認する」オンで、起動時にトークンが削除される。権限OFFで `off` が1回だけ発行される。
  - 権限の判定（全部含む／余分があってもよい／一方だけ・なしはNG）、トークンの読み込み（有効・権限不足・壊れたJSON）。
  - `RefreshError`（`invalid_grant`／その他／文字列の応答）、通信エラー、`HttpError`（403 `accessNotConfigured`・`SERVICE_DISABLED`（details形式）・`rateLimitExceeded`・`insufficientPermissions`・`forbidden`、503）の分類。
  - 起動時の状態が1回だけ発行される。1分の時点でブラウザ待ちなら `waiting`、それ以外なら `connecting`。
  - 承認後、通常は `oauth_token.json` を保存し、「毎回承認する」オンなら保存しない。`client_secret.json` がなければ分類1・メッセージ1件・`failed`。
  - API無効はメッセージが1回だけで、両方のAPI名が入る。起動中のトークン無効は `failed` になり、以降は取得しない。通信エラーはメッセージなしで `authenticated` のまま。

## 5. 追加対応: カレンダーID指定の扱い（2026-11-02）

### 決めたこと
- 取得対象は「マイカレンダー全体（`accessRole=="owner"`）」を基本とする。カレンダーIDでの絞り込み・追加は普通のユーザーには難しく、使われにくいため、設定画面からは隠す。
- ただし機能としては残し、`config.json` の `GoogleCalendar.CalendarIds` を直接書けば使えるようにする（分岐は数行で、他の処理と絡まないため）。
- ID指定の分岐は表示名にIDをそのまま入れていた（`summary=cid`）。メインカレンダーのIDはメールアドレスなので、AIにメールアドレスが渡っていた。表示名を次のように決めるよう直した。
  - calendarListにあるID: 自動取得と同じく `_resolve_calendar_display_name`（`summaryOverride` → カレンダー名 → 「メインカレンダー」）。
  - `primary`、または自分のメールアドレスのID: 「メインカレンダー」。
  - calendarListに見つからないID: 「カレンダー1」「カレンダー2」…の連番（見つからなかったものだけで数える）。
- 置き換え後の名前は「ユーザー名」も検討したが、AIが値の入る欄の名前と受け取りやすく、自動取得側の代替名とも揃わないため「メインカレンダー」にした。

### 変更したファイル
| ファイル | 内容 |

| `services/config_controller.py` | `GoogleCalendar.CalendarIds` の定義に `"hidden": True` を追加 |
