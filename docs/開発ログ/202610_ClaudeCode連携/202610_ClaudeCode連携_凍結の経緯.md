# ClaudeCode連携 凍結の経緯

**状態:** 2026-10-13 凍結（実装未着手のまま、要件定義の段階で停止）
**関連:** `202610_ClaudeCode連携_要件定義.md`（凍結時点の検討内容をそのまま残している）
**後継テーマ:** ローカルLLM（Ollama）によるPKM探索・応答の再現（新規に要件を立てる）

---

## 1. 当初の目的

- ローカルLLMは応答に時間がかかり、GeminiAPIは従量課金で金額がかさむ。
- ClaudeCodeの `-p`（非対話モード）を使えば、定額のサブスクリプションの範囲で高性能なLLMを利用でき、**応答速度と金銭面の両方を解消できる** と考えた。
- 配布版には規約の観点から含めず、作者個人の環境でのみ動く機能とする想定だった。

---

## 2. 検討の流れ

### 2.1 現状確認と課題の洗い出し（2026-10-13）
既存コード（`AI_main.py` のバックエンド切替、`UI_settings.py` の静的import、`main.spec`、`config_controller.py` の設定定義）とローカルの `claude` CLI（2.1.295）を確認し、以下の課題を整理した。

- **方式**：Claude Agent SDKはPython 3.10以上が必要で、winrtの制約でPython 3.9固定の本アプリでは使えない。CLIをsubprocessで呼ぶ方式しかない。
- **`--bare` が使えない**：最小構成モードはOAuthを読まず `ANTHROPIC_API_KEY` のみで認証するため、サブスクリプション利用と両立しない。
- **CLI特有の問題**：npmシム（`claude.cmd`）の解決、cmd.exeのコマンドライン長制限（8191文字）、cp932による文字化け、`--noconsole` 時のコンソール窓、`.cmd`→nodeのプロセスツリー残留、`ANTHROPIC_API_KEY` による意図しない従量課金、CLAUDE.md・MCP・プラグインなど余計なコンテキストの読み込み、セッション履歴の蓄積。
- **性能と利用枠**：1回ごとのCLI起動オーバーヘッド（数秒）。ReActとの組み合わせでは呼び出し回数が増える。5時間ごとの利用枠を定期要約が消費する。
- **規約**：第三者製品でのClaude.aiログイン／利用枠の提供は認められていない。無人の定期実行もグレー寄り。
- **配布・公開**：PyInstallerは `try` 内の静的importも追跡して同梱する。`ai_tools/*.py` はdatasとして丸ごと同梱される。

### 2.2 方針の決定
- 期待する能力はテキスト生成のみ。ただしThinking（推論）は活用する（`--effort`）。
- 会話応答とアクティビティ要約の両方に使う。
- PKMフォルダ直下を作業フォルダとし、CLAUDE.mdにアプリ用の要件を記載する。PKMは読み取りのみ（Read/Glob/Grep）。
- ReActはオミットし、`AI_Manager` と並ぶ別ラインとして実装する。`req_LLM` の呼び出し規約と応答イベントは共通にする。
- 当初は非公開の `private/` フォルダに置く案だったが、**通常のフォルダに置き、公開用リポジトリ作成時（`scripts/make_portfolio_repo.py`）と配布ビルド時（`main.spec` excludes + `sys.frozen`）に除外する** 方針に修正した。

### 2.3 ローカルLLMでのPKM利用の検討
PKMの利用をローカルLLMでも行いたいという要望から、ClaudeCodeの動作を分解して再現方法を検討した。

- ClaudeCodeの動作は「道具（Glob/Grep/Read）」「エージェントループ」「それをこなせるモデル」の3つに分解できる。
- 道具は `ai_tools` に読み取り専用のPKMツールとして追加でき、ループは既存のReActをOllamaのネイティブツール呼び出し（`tools` パラメータ）に移すことで実現できる。
- 品質と速度はClaudeに劣るが、索引による当たり付けや結果の切り詰めで補える見込み。
- ここで、**ClaudeCodeラインではReActを外し、ローカルLLMラインではReActを育てる** という非対称な構造になることが分かった。

### 2.4 凍結の判断
上記を踏まえ、ClaudeCode連携を凍結し、ローカルLLMでの再現を改めて目標とした。

---

## 3. 凍結の理由

1. **当初の目的が十分に達成できない**
   - 速度：CLI起動の数秒に加え、Thinkingの分だけ待ち時間が伸びる。速度面での優位は小さい。
   - 金銭：定額ではあるが、5時間ごとの利用枠を要約が消費し、会話用の枠を圧迫する。
2. **CLI特有の課題が多い**：2.1節の対策をすべて入れる必要があり、CLIのオプションや出力形式は更新で変わりやすいため保守の負担が大きい。
3. **プライバシーとセキュリティ**：アクティビティログやPKMの内容を外部に送信しないこと自体に価値がある。ローカルで完結すれば、規約のグレーさや公開・配布時の除外の手間もなくなる。
4. **ローカルLLMでの再現に見通しが立った**：ある程度の遅延と性能差を受け入れれば、同じ仕組みをローカルで組める。

## 4. 後継テーマへ引き継ぐもの

| ClaudeCode連携で検討した内容 | ローカルLLMラインでの使い道 |
|---|---|
| 応答待ちのUX（考え中の表示など） | そのまま必要 |
| PKMは読み取りのみ・パス検査・除外フォルダ | PKMツールの要件 |
| 出力構造をschemaで強制する | Ollamaの `format` / `tools` で同様に行う |
| `_parse_ai_response` の切り出し、バックエンド登録表 | 今後のバックエンド追加の下地 |
| 会話・要約で推論の深さやモデルを分ける | Ollamaの `think` やモデルの使い分けで行う |
| PKMの設定（ルート・除外フォルダ・アクセス規則） | ローカルLLM側の設定として定義する |

### 4.1 凍結時点で確認した環境（2026-10-13）
- GPU：NVIDIA GeForce RTX 3070（VRAM 8GB）
- Ollama 0.35.1。`/api/show` の `capabilities` でモデルごとの機能を取得できる。
- 導入済みモデルの機能（`/api/show` で取得）

| モデル | パラメータ / 量子化 | capabilities |
|---|---|---|
| `gemma4:e2b-huggingface-q8`（現在の設定） | 4.6B / Q8_0 | completion, tools, thinking |
| `gemma4:e2b` | 5.1B / Q4_K_M | completion, vision, audio, tools, thinking |
| `gemma3:4b` | 4.3B / Q4_K_M | completion, vision |
| `gemma3:12b` | 12.2B / Q4_K_M | completion, vision |
| `hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ1_M` | 34.7B / IQ1_M | completion, vision, tools, thinking |
| `embeddinggemma:latest` | 307M / BF16 | embedding |

- 同じGemma4 e2bでもタグによってvisionの有無が異なる。**機能はモデルファミリーではなくタグ単位で判定する必要がある。**
- 現在の `AI_ollama.py` は `think`・`tools`・`options`（`num_ctx` 等）を指定していない。

## 5. 再開の条件

以下のいずれかに当てはまる場合、本要件定義を起点に再開を検討する。

- ローカルLLMでは会話・PKM探索の品質が実用に届かないと判明した場合。
- 公式に、個人アプリからサブスクリプション利用枠を使う手段（または規約）が明確になった場合。
- CLIの起動オーバーヘッドが大きく改善された場合。

再開時は `202610_ClaudeCode連携_要件定義.md` の「6.1 実機で要検証」から着手する。除外設定（`make_portfolio_repo.py` の `*ClaudeCode連携*` glob）は資料の除外も兼ねているため、凍結中も残しておく。
