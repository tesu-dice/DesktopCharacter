## 2. LLMキューシステム：方針との比較

比較対象は改訂版の `LLMQueue_設計方針.md`（キュー部分に特化した最新版）。

| 項目 | 方針 | 実装 | 判定 |
|------|------|------|------|
| 優先度定数 | `LLM_PRIORITY_USER/PROACTIVE/SUMMARY/PROFILE` = 1〜4 | `ai/AI_main.py:38-42` に同名・同値で定義 | ✅ 一致 |
| キュー構造 | `queue.PriorityQueue` に `(priority, counter, task)` | `_llm_queue`（`PriorityQueue`）、`_queue_counter` を `_queue_lock` で保護しつつ採番 | ✅ 一致 |
| ルーティングテーブル `self._route` | `response_event → (priority, handler)` を `__init__` に定義 | `OnUserResponse→(USER,_do_response)`, `OnSummaryDone→(SUMMARY,_do_summary)` を実装 | ✅ 一致 |
| 公開インターフェース `req_LLM()` | 未知の `response_event` は warning ログのみで無視 | 同様に `self._route.get()` が `None` の場合 warning を出して return | ✅ 一致 |
| `_do_response()` | `response_event` をハードコードせず引数で publish | 実装済み。ReAct分岐・通常応答分岐の両方で `bus.publish(response_event, ...)` | ✅ 一致 |
| `_do_summary()` | `scope`/`time`/`data`/`reply_to` を展開しプロンプト分岐、完了後 `(time_str, scope, reply_to, result_text)` をpublish | ほぼ同一プロンプト文言で実装、publish引数も一致 | ✅ 一致 |
| サマリーイベントの1本化 | `Req_UserSummaryLog` の1イベントに統合 | `UserDataLogger.request_summary()` が単一イベントをpublish、`main.py` が `handle_summary_request` で受けて `req_LLM` に橋渡し | ✅ 一致 |
| 削除対象（方針8章） | `response()`/`response_withRAG()`/`make_rag_request()`/`response_onetime()`/RAG関連購読/`Check_responseMode()`/`AIGenerateMessage`イベント/2イベント構成のサマリー | 全て削除・置換を確認 | ✅ 一致 |
| `priority`引数を`req_LLM`から排除（方針10章の設計変更） | 呼び出し側は`response_event`のみ渡す | `main.py: handle_user_message/handle_summary_request` は`response_event`のみ指定 | ✅ 一致 |

**キュー部分は方針ファイルの記述をほぼそのままなぞる形で実装されており、乖離は見当たらない。**

### 方針にない追加実装（キュー周辺）

- `UserDataLogger._to_markdown_table()`：ログをJSON文字列ではなくMarkdownテーブル化してからLLMに渡す処理を追加。方針ファイルには入力データのフォーマットに関する規定がなく、トークン削減を狙った独自の改善と見られる。

## 3. ユーザープロファイル機能：方針との比較

比較対象は当初方針の `LLMQueue_and_UserProfile_設計方針.md`（3章・4章）。こちらは改訂版方針（7/1付）には引き継がれず「9. 未解決・将来課題」で「別設計書参照」とだけ触れられている部分。

| 項目 | 方針（3章・4章） | 実装 | 判定 |
|------|------|------|------|
| ファイル構成 | `user_profile_stable.json`（安定情報）+ `user_profile_recent.json`（直近傾向）、いずれも `user_logs/` 配下 | `user_profile.txt`（APP_DIR直下、平文）+ `user_logs/user_profile_recent.md`（Markdown） | ⚠️ 形式・配置ともに簡略化 |
| フォーマット | JSON（構造化） | プレーンテキスト／Markdown、`//`始まりの行はコメントとして除外 | ⚠️ 変更（人間が直接編集しやすい形式を優先したと見られる） |
| プロンプトへの組み込み | `init_prompt`末尾に追加 | `character_context_text`と統合し`_do_response`の通常応答時に付加。さらに`react_planing`の思考プロンプトにも`user_profile_text`をそのまま挿入 | ✅ 組み込み範囲は方針より広い（ReAct時も参照する） |
| 自動更新（起動時チェック→N日経過で更新） | 4章で明記 | **未実装**。読み込み専用で、書き込み・更新ロジックはコード上に存在しない | ❌ 未実装 |
| 更新頻度設定（週1回推奨） | 4.2章 | **未実装** | ❌ 未実装 |
| `LLM_PRIORITY_PROFILE`のルーティング（`OnProfileDone`） | 想定イベント | 定数のみ定義済み、`self._route`に未登録・ハンドラなし | ❌ 未実装 |
| 直近7日サマリーからの自動抽出プロンプト | 4.3章 | **未実装** | ❌ 未実装 |

**ユーザープロファイルは「読み込んでプロンプトに反映する」導線のみ実装済みで、方針の中核であった自動更新の仕組み（起動時チェック・週次更新・専用LLMリクエスト）はまだ手がついていない。** `user_profile.txt` は `.gitignore` に追加されており運用は手動編集を前提にしていると見られるが、`user_profile_recent.md` を書き込む処理がコード上どこにもないため、現状は空ファイルか手動更新頼みの状態。
