# GCalの認証情報保持 要件定義

**対象:** DesktopCharacter / `collectors/GoogleCalendarCollector.py`（認証・トークンの保存・権限の判定）, `main.py`（起動時メッセージ、イベントの配線、`Req_CalendarInfo` の発行条件）, `services/config_controller.py`（権限の説明文、チェックボックスの設定項目。1.8節）, `ai_tools/get_calendar_info_tool.py`（説明文のみ）, `collectors/GoogleCalendarAPI.py`・`collectors/GoogleCalendarAPItest.py`（トークンをファイルに保存しないよう変更。1.14節）

# 概要
アプリケーションをWindowsのタスクスケジューラで毎朝起動するようになったので、Googleカレンダーの連携をより簡単にしたい。そのため、これまでは起動時に毎回ブラウザでの認証を求めていたが、GCPのOAuth同意画面の公開ステータスを「本番」（未審査）へ変更し、認証トークンをローカルファイルとして保存することで認証のための操作を毎回しなくていいようにする。  
また、GCPを本番環境にしたことで認証トークンをリフレッシュできるようになり、一回承認したらそのあとは削除しなければ自動的に承認されるようになるはず。  
Boothの配布においてはアプリのクライアント情報（`client_secret.json`）は同梱せず、ユーザ自身にGCPの設定をしてもらって連携してもらうようにしたい。そのうちやってもいいけど、GCPの認証人数は現状だと100人制限がかかるので少なくともGCPでアプリの承認をもらってからかな。  
起動時にトークンを取得後、認証情報はJsonファイルでローカルに保存する形で管理。設定UIにはカレンダー連携に関するON/OFF情報とトークン情報が表示されるようにする。(テキスト形式で編集可能)（→1.8節で見直し）
- メッセージ機能
アプリ起動時のタイミングで権限が許可された項目を一覧で表示、連携が成功しているかをメッセージとして記載する。
失敗の際にはその詳細をある程度分類して別途メッセージを表示する。

- OFFにした際の挙動  
基本的に変更後に再起動を推奨し、その起動中には内部的な扱いは変わらないものとする。  
次回起動時に設定を参照し、OFFの場合は該当情報の削除や初期化を行う。  

**用語:** `client_secret.json` は「どのアプリか」を表すクライアント情報（GCPで作成し、ユーザーが配置する）。保存するトークンは、ユーザーがブラウザで承認した結果として得られるアクセス権で、別物。

## 1. 決定事項

### 1.1 権限の判定はCollectorが持つ
- `GoogleCalendarCollector` が起動時の権限の値を保持し、その起動中はその値だけで動く（起動中に設定を変えても扱いは変わらない）。
- `main.py` の `update()`（5分ごと）と `handle_user_message()`（会話開始時）は権限を見ずに `Req_CalendarInfo` を発行し、取得するかどうかはCollectorが判定する。
  - 現状は `main.py` 側が保存後の設定（`myapp.setting`）を見ているため、起動中にOFFにするとその時点で取得が止まる。概要の「起動中には内部的な扱いは変わらない」と合わないため、判定をCollectorに寄せる。
- 理由: カレンダー連携が「この起動で有効か」を決める責任を1か所にまとめるため。AIツールの権限も `ToolExecutor` が起動時の値を持ち続けており（`202610_ツール権限の徹底_要件定義.md` 3.5節）、扱いがそろう。

### 1.2 権限の変更の反映
- 権限の説明文（`services/config_controller.py` の `get_calendar_info` の `description`）に、変更は起動し直した後に反映されることを書く。文言はツール共通の一文「変更はアプリを終了して起動し直した後に反映されます。」に合わせる（`202610_ツール権限の徹底_要件定義.md` 3.5節）。
- 起動し直しは、ユーザーが手動でアプリを終了して起動する。アプリ側で再起動を促すポップアップなどは出さない。
- 次回起動時に権限がOFFなら、該当情報を削除・初期化する（対象は1.9節）。

### 1.3 起動時メッセージ
- 既存の起動時メッセージ（`main.py` の `app_start_message`）に、Googleカレンダー連携の結果を載せる。
- 認証は非同期で進むため、起動時メッセージは連携の結果を**最大1分**待ち、その時点の結果を表示する。

| 1分の時点の状態 | 表示 |
|---|---|
| 権限OFF | 連携しない（OFF） |
| 連携に成功 | 成功 |
| ブラウザでの承認待ち | 承認待ち（ブラウザで承認してください） |
| ブラウザは開いていないが処理中（トークンの更新や初回の取得の通信が終わっていない） | 接続中（つながると自動で連携します） |
| 失敗 | 失敗（1.5節の分類名） |
| 通信エラー（1.5節の分類4） | 通信エラー（ネットワークにつながると自動で連携します） |

- 失敗の詳細は、1.5節に従って別のメッセージで表示する。
- 「接続中」は、保存済みのトークンで連携しようとしたが通信が遅く、1分の時点で結果が出ていない場合。ブラウザは開いていないため「承認待ち」とは出さない。また、その後に成功してもメッセージは出ない（1.10節）ため、「通信エラー」と出すと表示が実際とずれる。そのため別の状態にする（2026-10-26決定）。その後に失敗した場合は1.10節どおり別のメッセージで知らせる。
- 失敗の詳細のメッセージは、起動時メッセージより先に出ることがある。Collectorは結果が出た時点で出し、起動時メッセージはVOICEVOXの起動・AI接続確認も待つため。順番をそろえるには `main.py` 側の作り込みが要り、4.1節の「Collectorの外への変更は最小限」に反するため、そろえない（2026-10-26決定）。
- 分類4（通信エラー）は自動で戻るため、「失敗」とは表示しない（利用者が何かしないといけないと思わないように）。
- 「権限が許可された項目を一覧で表示」はカレンダー以外の権限にも関わるため、ツール権限の要件定義と内容をそろえる。
- 1分待つ間は、起動時メッセージ全体（バージョン情報・AI接続確認を含む）の表示が遅れる。保存済みのトークンで連携できる通常の起動では、待ち時間はほとんどない想定。
- 認証に成功したら、すぐに1回予定を取得する。現状は5分ごとの定期取得（時刻の分が5の倍数のとき）か会話の開始まで取得しないため、起動直後にAIへ予定を尋ねると「まだ取得できていません」になる。また、すぐに取得することで、分類5（1.5節）も起動時メッセージの時点で分かる。
- 「成功」は、予定の取得まで成功したことを指す。

### 1.4 ブラウザでの承認待ち
- 承認待ちのタイムアウトは**5分**。過ぎたら1.5節の分類2として扱う。
- 現状はタイムアウトがなく、ブラウザを閉じたり放置したりするとアプリを終了するまで待ち続ける。

### 1.5 失敗の分類

| # | 分類 | 主な原因 | トークン | ユーザーへの案内 |
|---|---|---|---|---|
| 1 | `client_secret.json` の問題 | ファイルがない、形式が正しくない | 残す（ファイルを戻せば連携が続くように） | 配置し直して、アプリを終了して起動し直す |
| 2 | 承認できなかった | 同意画面で拒否した、5分以内に承認しなかった、カレンダーとタスクの一方だけ許可した、承認後のトークンの受け取りが通信エラーで失敗した、認証中の想定外のエラー（ローカルのポートが使えない など） | （まだない） | 連携する場合は、アプリを終了して起動し直す。一方だけ許可した場合は、両方にチェックを入れるよう伝える |
| 3 | トークンが無効 | Google側で失効・取り消し（`invalid_grant` 等）、ファイルを読めない、使う権限（カレンダー・タスク）がトークンに含まれていない | 承認し直して上書きする | 起動時: そのままブラウザでの承認に進む。起動中: ブラウザは開かず、アプリを終了して起動し直すよう知らせる |
| 4 | 通信エラー | ネットワーク未接続、Google側の一時的な障害 | **残す** | 不要。次の定期取得で自動的に再試行する |
| 5 | 予定を取得できない | GCPでGoogle Calendar API / Google Tasks API が有効になっていない（取得時に403で、理由が `accessNotConfigured` 等。10.3節） | 残す | GCPで両方のAPIが有効になっているか確認する |

- 4は「削除しない」ことが重要。朝の自動起動直後にネットワークがまだつながっていなくても、つながった時点で自動的に連携が戻るようにする。
- 4は起動時メッセージに記載するだけで、別のメッセージは出さない。起動中に起きた場合はログのみ（Wi-Fiの一時的な切断などのたびに出さないため）。
- 5は、認証は通るが予定を取れない場合。それ以外の取得エラー（利用回数の上限による403などを含む）の振り分けは10.3節に従い、基本はログのみとする（一部のカレンダーだけ失敗した場合も、他のカレンダーの取得は続ける。現状の動きのまま）。
- 2の「承認後のトークンの受け取りの通信エラー」と「想定外のエラー」は、トークンがまだないため4の「残して再試行」ができず、利用者がすること（アプリを終了して起動し直す）も2と同じため、分類を増やさずに2に含める（2026-10-26決定）。原因はログに残す。
- 同じ内容のメッセージは、1回の起動につき1回まで（5分ごとの定期取得のたびに出さないため）。
- メッセージにはトークンの中身や例外の詳細を出さない。詳細はログに残す。

### 1.6 保存形式
- トークンは、アプリ直下（exe化時はexeと同じフォルダ）の `oauth_token.json` に平文のJSONで保存する（暗号化は今回は見送り）。
- `oauth_token.json` は `.gitignore` と `scripts/make_portfolio_repo.py` の除外リストに登録済み。

### 1.7 配布用readme
- GCPの設定手順、トークンの失効条件、連携の解除方法などは `開発予定/readmeファイルの更新.md` で管理する。

### 1.8 設定UIでの表示（2026-10-25決定、2026-10-26変更）
概要の「トークン情報を表示・テキストで編集可能」は、次の理由で採らない。
- 設定画面は一度作ったものを使い回し（`ui/UI_main.py` の `show_settingUI`）、「設定を反映」で画面上のすべての値を書き戻す（`ui/UI_settings.py` の `save_and_apply_settings`）。トークンを設定項目として持たせると、設定画面を開いた後に認証が終わった場合、その後の保存で古い値（初回なら空）に戻ってしまう。
- トークンを画面に出すと、画面共有・配信・スクリーンショットで漏れる。
- トークンはユーザーが手で作れないため、編集で役立つのは「空にして承認し直す」程度。

代わりに、`ApplicationSettings.GoogleCalendar` の欄に「毎回承認する（承認情報を保存しない）」チェックボックス（`bool` の設定項目、既定False）を1つ置く。
- 既存の汎用の設定画面で自動的に表示されるため、`ui/UI_settings.py` の変更は不要。
- **オンの場合:** 起動時、Collectorの初期化の中でトークン（`oauth_token.json`）があれば削除する。承認後のトークンはファイルに保存せず、メモリの中だけで扱う。起動のたびにブラウザでの承認になる。
- **オフの場合:** トークンを `oauth_token.json` に保存し、次回から自動で連携する（本機能の通常の動き）。
- 値はユーザーが切り替えるもので、アプリから書き換えない。そのためCollectorは `config.json` を書き込まない（当初案の「次回起動時にトークンを削除する」は、起動時にアプリがチェックを外して保存する必要があり、画面上の値との食い違いで起動のたびに削除される不具合の元になるため採らない）。
- 権限と同じく起動時の値を写し取って使い、変更は起動し直した後に反映される（1.1節・1.2節）。
- 権限がオフのときは、この設定に関わらず1.9節のとおりトークンを削除する。
- 承認し直したいときは、`oauth_token.json` を手で削除して起動し直す（readmeで案内）。この設定を一度オンにして起動し、オフに戻して起動し直しても同じ結果になる（承認は2回になる）。

連携状態（連携済み／未連携）は設定画面には表示せず、起動時メッセージ（1.3節）に任せる。設定画面には読み取り専用の表示欄がなく、表示するには表示用の型の追加・Collectorへの問い合わせ・画面を開くたびの取り直しが必要になるため。毎朝の起動時メッセージで結果は分かる。

### 1.9 OFF時に削除する対象（2026-10-25決定）
- トークン（`oauth_token.json`）を削除する。
- 予定のキャッシュ（`google_calendar_cache.json`）は、現状でも起動時・終了時に削除している。
- Google側の同意の取り消し（`revoke`）は行わない。取り消しは「Googleアカウント×クライアント」単位で効くため、同じ `client_secret.json` を使う他のPCの連携まで切れる。Google側の同意を消したい場合は、ユーザーがGoogleアカウントの「サードパーティ製アプリとサービス」から削除する（readmeで案内）。

### 1.10 1分を過ぎてから結果が出た場合（2026-10-25決定）
- 失敗は1.5節に従って別のメッセージで知らせる。
- 成功はメッセージを出さず、ログのみ。

### 1.11 トークンを保存できなかった場合
- 書き込みに失敗した場合（exeを書き込み禁止のフォルダに置いた場合など）は、ログに残し、その起動の間は連携を続ける。次回の起動では再びブラウザでの承認になる。
- `config.json` の保存も同じ制約を受けるため、新しい問題ではない。メッセージは出さない。

### 1.12 起動中のトークンの更新
- アクセストークン（約1時間で切れる）の更新は、ライブラリが取得のたびに自動で行う。起動中に更新したトークンはファイルに保存し直さない（リフレッシュトークンが変わらないため、次回の起動時にまた更新すればよい）。
- 起動時に保存済みのトークンを更新した場合も、同じ理由でファイルに保存し直さない（毎朝の起動のたびにファイルを書かずに済む。2026-10-26決定）。
- 起動時に分類4（通信エラー）で更新できなかった場合も、そのまま取得を試みる状態にしておけば、次の取得でライブラリが更新を再試行する。「再試行待ち」の状態を別に持つ必要はない。

### 1.13 説明文・コメントの更新
| 場所 | 対応 |
|---|---|
| `services/config_controller.py` の `get_calendar_info` の説明文（設定画面・ユーザー向け） | 「利用にはclient_secret.jsonの配置と、起動時のGoogle認証が必要です。」を、「利用にはclient_secret.jsonの配置が必要です。初回のみブラウザでの承認が必要で、以降は自動で連携します。」のような内容にし、末尾に1.2節の一文を付ける |
| `ai_tools/get_calendar_info_tool.py` の `description`（AI向け） | `client_secret.json` や認証の話はAIの判断に不要なため削除する |
| `collectors/GoogleCalendarCollector.py` 冒頭のdocstring | 「認証トークンはファイルに保存しない」を、トークンを `oauth_token.json` に保存することに書き換える。参照先の設計方針のパスを `docs/開発ログ/202608_カレンダー連携/` に直し、本書も参照先に加える |
| `GoogleCalendarCollector` の認証まわりの関数のdocstring | 「トークンファイルへの書き込みは行わない」など、実装に合わせて更新する |

### 1.14 旧ファイルの扱い（2026-10-26変更）
- `collectors/GoogleCalendarAPI.py` と `collectors/GoogleCalendarAPItest.py` は、アプリからは使われていないが、手動で使うことがあるため**残す**。
- ただし、どちらも本機能と同じファイル名の `oauth_token.json` に、読み書き用スコープのトークンを平文で書き込む（`GoogleCalendarAPItest.py` は読み込みもする）。本機能のトークンを上書きしたり、本機能のトークンを読んだりしないよう、**トークンをファイルに保存せず、メモリの中だけで扱う**ように変更する（実行のたびにブラウザで承認する）。
  - `oauth_token.json` の読み込み・書き込みの処理と、定数 `OAUTH_TOKEN_FILE` を削除する。
  - スコープ（読み書き用）はそのままにする。ファイルを共有しなくなるため、本機能のトークンとはぶつからない。
- 開発環境に残っている、これらが作った `oauth_token.json` は、本機能が使う権限を含んでいればそのまま使われ、含んでいなければ分類3として承認し直しになる。追加の移行処理は作らない。

## 2. 実装時の注意
- **権限の不足の判定（2026-10-26決定）:** スコープの完全一致は見ず、本機能が使う権限（Collectorの `SCOPES`）がトークンにすべて含まれているかだけを判定する（余分な権限があってもよい）。スコープの変更はアプリ側では扱わない。`Credentials.from_authorized_user_info(info, scopes)` に `scopes` を渡すと、保存されているスコープが渡した値で上書きされ、不足を見落とす。`scopes` を渡さずに読み込むか、JSONの `scopes` を直接確かめる。
- **同時実行:** 5分ごとの取得と会話開始時の取得は、EventBusによって別々のスレッドで同時に動くことがある。`googleapiclient` が使う httplib2 はスレッドセーフではないため、`refresh_cache()` 全体に1本のロックをかけて直列にする。ブラウザでの承認待ち（最長5分）の間は、このロックを持たない。
- **承認待ちのタイムアウト:** `run_local_server(timeout_seconds=300)` を指定する。時間が過ぎると、ライブラリは専用の例外ではなく `AttributeError` を出す（受け取ったURLが `None` のため）。
- **トークン無効の判定:** 分類3にするのは、更新時の `RefreshError` が `invalid_grant`・`invalid_client`・`unauthorized_client` のときと、ファイルを読めない・使う権限が含まれていないときだけ。それ以外のエラーはすべて分類4として扱い、トークンを残す（`RefreshError` はGoogle側の一時的な5xxエラーでも出るため）。
- **ログ:** 例外の内容をそのまま出すと、Googleからの応答本文が含まれる。トークンの中身が出力されないことを確認する。

## 3. 確認項目
実装後に手動で確認する項目。

| # | 確認内容 | 再現方法 | 期待する結果 |
|---|---|---|---|
| 1 | 初回の承認 | `oauth_token.json` がない状態で権限をオンにして起動 | ブラウザが開き、承認後に `oauth_token.json` が保存される。起動時メッセージに「成功」と出て、すぐにAIが予定を答えられる |
| 2 | 2回目以降の起動 | 1の後に起動し直す | ブラウザが開かずに連携できる |
| 3 | 起動時の通信エラー | 機内モードで起動し、しばらくしてから接続する | トークンは残り、起動時メッセージに通信エラーと出る。接続後の定期取得で自動的に連携が戻る |
| 4 | 承認の拒否 | 同意画面で「キャンセル」を押す | 分類2のメッセージが出る。起動し直すとブラウザでの承認に進む |
| 5 | 承認待ちのタイムアウト | ブラウザを閉じて5分待つ | 起動時メッセージに「承認待ち」、5分後に分類2のメッセージが出る |
| 6 | 一方だけ許可 | 同意画面でタスクのチェックを外して承認する | 分類2のメッセージで、両方にチェックを入れるよう案内される |
| 7 | アクセスの削除 | Googleアカウントの「サードパーティ製アプリとサービス」からアクセスを削除して起動 | ブラウザでの承認に進む。起動中に削除した場合は、ブラウザは開かず分類3のメッセージが1回出る |
| 8 | 権限OFF | 権限をオフにして保存し、アプリを終了して起動し直す | 保存してから終了するまでは連携が続く。起動時に `oauth_token.json` が削除され、起動時メッセージに「連携しない（OFF）」と出る |
| 9 | 毎回承認する | 連携済みの状態で「毎回承認する」をオンにして保存し、終了して起動し直す。続けてもう一度起動し直し、最後にオフに戻して起動し直す | オン後の起動で `oauth_token.json` が削除され、ブラウザでの承認に進む。承認後もファイルは作られず、次の起動でも承認になる。設定画面のチェックはオンのまま。オフに戻した後の承認で `oauth_token.json` が保存され、その次からは自動で連携する |
| 10 | `client_secret.json` の問題 | 連携済みの状態で、ファイルを削除、または中身を壊して起動 | 分類1のメッセージが出る。トークンは残り、ファイルを戻して起動し直すとブラウザが開かずに連携できる |
| 11 | APIが無効 | GCPでGoogle Calendar APIを無効にして起動 | 分類5のメッセージが1回だけ出る |
| 12 | ログ・メッセージ | 上記の各操作後に `application.log`・コンソール出力・メッセージを確認 | トークンの中身が出力されていない |
| 13 | exe版 | PyInstallerでビルドしたexeで1・2を確認する | 開発環境と同じ動きになる |
| 14 | 承認後の通信エラー | 同意画面を開いた状態で機内モードにしてから承認する | 分類2のメッセージが出る。原因がログに残る |
| 15 | 旧ファイル | `collectors/GoogleCalendarAPI.py` を手動で実行する | ブラウザで承認して動き、`oauth_token.json` が作られない・変わらない |

## 4. 構成の方針

1〜3章で決めた内容について、どのファイル・クラスが何を受け持ち、どこがどのイベントでつながるかを決める。引数や戻り値などの細部は詳細設計で決める。

### 4.1 主な方針
1. **カレンダー連携に関することは `GoogleCalendarCollector` にまとめる。** 権限の判定、トークンの読み書き・削除、失敗の分類、カレンダー連携のメッセージ表示は、すべてCollectorが受け持つ。他のモジュールは権限やトークンを見ない。
2. **他のモジュールとはEventBusだけでつながる。** `main.py` はCollectorのメソッドを直接呼んで結果を待たない。起動時メッセージへの結果の受け渡しも、既存の `subscribe_when` による合流で行う（6章）。
3. **既存の仕組みをそのまま使う。** EventBus・設定画面・ポップアップ（`Req_PopUpMessage`）・AIツールの仕組みには手を加えない。
4. **Collectorの外への変更は最小限にする。** `main.py` は配線と起動時メッセージの表示だけ、`config_controller.py` は設定項目と説明文だけを変える。

### 4.2 ファイルを分けない理由
トークンの読み書きを別のモジュール（例: `collectors/google_token_store.py`）に分ける案もあるが、トークンを使うのはCollectorだけで、処理も読み込み・保存・削除の3つと小さい。個人開発で追いやすいよう、Collectorの中の非公開メソッドとして持つ。

## 5. 全体の流れ

### 5.1 起動時
```
main.py (myapp.__init__)
  └─ GoogleCalendarCollector(bus, setting, app_dir)   … 同期処理のみ
        ├─ キャッシュの削除（現状どおり）
        ├─ 権限と「毎回承認する」の値を写し取る（1.1節・1.8節。以降は設定を見ない）
        ├─ 権限OFF かつ トークンあり → トークンを削除（1.9節）
        └─ 「毎回承認する」がオン かつ トークンあり → トークンを削除（1.8節）

main.py (_setup_event_listeners の後)
  └─ publish("application start")
        ├─ ui.start_TTS_Server → publish("Start_TTS_Server", engine_process)   … 既存
        └─ CalendarCollector.start → 認証をバックグラウンドで開始（新規）
              ├─ 結果が出た時点、または開始から1分の時点で（早い方・1回だけ）
              │     publish("OnCalendarStartupStatus", status)
              └─ 失敗したら Req_PopUpMessage で分類ごとのメッセージ（1分後でも同じ）

subscribe_when(["Start_TTS_Server", "OnCalendarStartupStatus"], app_start_message)
  └─ 両方そろったら起動時メッセージを表示（serverid, calendar_status を受け取る）
```

- 認証の開始を `__init__` から `application start` の購読に移す。`__init__` の中で始めると、権限OFFなどですぐに結果が出た場合に、`subscribe_when` の登録（`_setup_event_listeners`）より前に `OnCalendarStartupStatus` を発行してしまい、結果が届かないため。
- 既存の `subscribe("Start_TTS_Server", app_start_message)` は、この `subscribe_when` に置き換える。
- Collectorは `OnCalendarStartupStatus` を**必ず1回**発行する（権限OFFのときも即座に発行する）。発行しないと起動時メッセージが出なくなるため、1分のタイマーで必ず発行されるようにする。

### 5.2 起動時の認証（Collector内部、バックグラウンド）
```
1. client_secret.json の確認 → ない・読めない → 分類1
2. oauth_token.json の読み込み
     ├─ ない → 3へ
     ├─ 読めない・使う権限が含まれていない → 分類3（ログのみ）→ 3へ
     ├─ 有効 → 4へ
     └─ 期限切れ → 更新
           ├─ 成功 → 4へ（保存し直さない。1.12節）
           ├─ invalid_grant 等 → 分類3（ログのみ）→ 3へ
           └─ それ以外 → 分類4（トークンを残して 4へ）
3. ブラウザでの承認（5分）
     ├─ 拒否・タイムアウト・一方だけ許可 → 分類2
     └─ 成功 → 保存（「毎回承認する」がオンなら保存しない。保存に失敗してもログのみで続ける。1.8節・1.11節）
4. calendar_service / tasks_service を作成し、auth_state = "authenticated"
5. すぐに1回取得する（1.3節） → 成功 / 分類5 / 分類4
6. 起動時の状態を確定して OnCalendarStartupStatus を発行（1分を過ぎていれば発行済み）
```

### 5.3 起動中
```
main.py update()（5分ごと） / handle_user_message()（会話開始時）
  └─ publish("Req_CalendarInfo")   … 権限を見ずに発行する（1.1節）

GoogleCalendarCollector.refresh_cache()
  ├─ auth_state が "authenticated" でなければ何もしない（権限OFF・失敗時もここで止まる）
  └─ ロックを取って取得 → キャッシュに書き込み
        ├─ invalid_grant 等 → 分類3: auth_state = "failed"、メッセージ（ブラウザは開かない）
        ├─ 403（APIが無効） → 分類5: メッセージ
        └─ それ以外 → 10.3節の振り分け（基本は分類4またはログのみ。次回の取得でライブラリが更新を再試行）
```

### 5.4 終了時
- 変更なし。`main.py` の `exit()` で、現状どおりキャッシュを削除する。トークンは終了時には触らない（削除は次回起動時。1.2節）。

## 6. イベント

| イベント | 発行元 | 購読先 | 引数 | 種別 |
|---|---|---|---|---|
| `application start` | `main.py` | `ui.start_TTS_Server`（既存）、`CalendarCollector.start`（追加） | なし | 既存 |
| `Start_TTS_Server` | `ui/UI_main.py` | `subscribe_when` による合流（変更） | `engine_process` | 既存 |
| `OnCalendarStartupStatus` | `GoogleCalendarCollector` | `subscribe_when` による合流 | 起動時の状態（6.1節） | **新規** |
| `Req_CalendarInfo` | `main.py` | `CalendarCollector.refresh_cache` | なし | 既存（発行条件を変更） |
| `Req_PopUpMessage` | `GoogleCalendarCollector`（追加） | `ui.show_message_box` | `type, title, message` | 既存 |

- イベント名は既存の命名（`OnUserResponse`・`OnSummaryDone` など、結果の通知は `On〜`）に合わせる。
- `Req_PopUpMessage` は、どのモジュールからでも使える汎用の表示要求として扱う。Collectorが自分のメッセージを直接発行することで、`main.py` が分類ごとの文言を知らずに済む。

### 6.1 起動時の状態
Collectorが `OnCalendarStartupStatus` で渡す値。文字列の定数としてCollectorのモジュールに定義する。

| 状態 | 意味 | 起動時メッセージの表示（1.3節） |
|---|---|---|
| `off` | 権限OFF | 連携しない（OFF） |
| `success` | 予定の取得まで成功 | 成功 |
| `waiting` | 1分の時点でブラウザでの承認待ち | 承認待ち（ブラウザで承認してください） |
| `connecting` | 1分の時点で、ブラウザは開いていないが処理中 | 接続中（つながると自動で連携します） |
| `client_secret` | 分類1 | 失敗（client_secret.jsonの問題） |
| `not_approved` | 分類2 | 失敗（承認できなかった） |
| `network` | 分類4 | 通信エラー（ネットワークにつながると自動で連携します） |
| `api_disabled` | 分類5 | 失敗（予定を取得できない） |
| `invalid_token` | 分類3（認証の直後の取得で出た場合） | 失敗（トークンが無効） |

- 分類3（トークンが無効）は、トークンの読み込み・更新の時点で分かれば、そのままブラウザでの承認に進むため、起動時の状態としては現れない（`waiting` か、承認の結果になる）。
- ただし、認証の直後の取得で分類3が出た場合（更新できた直後にGoogle側で取り消された、403 `insufficientPermissions` など）は、他のどの状態にも当てはまらないため `invalid_token` とする。まれな場合だが、表示を間違えないため（2026-10-26追加）。
- 状態から表示の文字列への変換は `main.py` の `app_start_message` が受け持つ。起動時メッセージの他の項目（バージョン情報・VOICEVOX）の文言も `main.py` が組み立てているため、それにそろえる。

## 8. クラス・モジュールごとの責任

### 8.1 `collectors/GoogleCalendarCollector.py`（`GoogleCalendarCollector`）
責任を次の5つに分け、それぞれを担うメソッドを置く。具体的なメソッド名・引数は詳細設計で決める。

| 責任 | 内容 |
|---|---|
| 起動時の準備（`__init__`、同期） | キャッシュの削除、権限と「毎回承認する」の写し取り、権限OFF時・「毎回承認する」オン時のトークン削除。ネットワークに触れる処理は行わない |

| トークンファイルの操作（非公開） | `oauth_token.json` の読み込み（使う権限が含まれているかの確認を含む）・保存（一時ファイルから置き換え、キャッシュの `_write_cache()` と同じ方式。「毎回承認する」がオンなら保存しない）・削除 |

## 10. 未解決・詳細設計で決めること

### 10.1 分類に当てはまらないエラー（2026-10-26決定）
1.5節の5分類に、次の場合が入っていない。
- ブラウザで承認した後、トークンの受け取りが通信エラーで失敗した場合（トークンがまだないため、分類4の「残して再試行」ができない）。
- 認証の処理中の想定外のエラー（ローカルのポートが使えない、など）。

決定: どちらも**分類2（承認できなかった）**として扱い、「アプリを終了して起動し直してください」と案内する（1.5節に反映済み）。

### 10.2 詳細設計で決めること
- Collectorのメソッド名・引数・戻り値。
- 例外から分類への対応表（`RefreshError` のエラーコードの取り出し方、`AccessDeniedError`・`Warning`（一方だけ許可）・タイムアウト時の `AttributeError` など）。
- 分類ごとのメッセージの最終的な文言と、ポップアップの種類（info / warning / error）。
- 起動時の状態の発行を1回だけにする仕組み（結果とタイマーのどちらが先でも、二重に発行しない）。
- 403の検知方法の細部（10.3節の方針に沿って、どのメソッドで記録・集約するか）。

### 10.3 分類5（APIが無効）の判定方針（2026-10-26）
403はAPIが無効なとき以外（利用回数の上限など）にも返るため、ステータスコードだけで分類5にしない。エラーの理由（reason）まで見て振り分ける。

**理由の取り出し方**
- `HttpError.status_code` でステータスコードを見る。
- 理由は `HttpError.content`（応答本文のJSON）から取り出す。`error.errors[].reason`（旧形式）と `error.details[].reason`（`ErrorInfo` 形式）の両方を見る。
  - `HttpError.error_details` は、本文に `details` と `errors` の両方があると `details` しか持たないため、これだけに頼らない。
  - `HttpError.reason` は理由ではなくメッセージ文なので、判定に使わない。
- 本文がJSONでない・理由が取れない場合は、下の表の「それ以外」として扱う。

**振り分け（案）**
| ステータス | 理由 | 分類 | 対応 |
|---|---|---|---|
| 403 | `accessNotConfigured`、`SERVICE_DISABLED` | 5 | どちらのAPI（Calendar / Tasks）が無効かをメッセージに含める |
| 403 / 429 | `rateLimitExceeded`・`userRateLimitExceeded`・`dailyLimitExceeded`・`quotaExceeded` など | 4 | ログのみ。次回の取得で再試行 |
| 403 | `insufficientPermissions`、`ACCESS_TOKEN_SCOPE_INSUFFICIENT` | 3 | 使う権限が足りない（読み込み時の確認をすり抜けた場合）。起動中はブラウザを開かず、起動し直すよう知らせる |
| 403 / 404 | `forbidden`・`notFound` など（`CalendarIds` で指定したカレンダーに権限がない・存在しない） | ログのみ | 他のカレンダーの取得は続ける（現状どおり） |
| 5xx | － | 4 | ログのみ |
| それ以外 | － | ログのみ | 現状どおり |

**403が出る場所**
- `_resolve_calendar_ids` の `calendarList().list()`。今は `HttpError` を捕まえて `primary` だけの取得に切り替えるため、Calendar APIが無効だとここで1回、続く `events().list()` でもう1回出る。どちらでも分類5として記録し、メッセージは1回にまとめる（1.5節の「1回の起動につき1回まで」）。
- カレンダーごとの `events().list()`。
