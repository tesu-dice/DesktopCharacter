## ローカルLLMでのPKM探索（2026-10-13 追記）

### 経緯
- ClaudeCode（`claude -p`）にPKMフォルダを読み取り専用で探索させる案を検討したが、CLI特有の課題・プライバシー・速度と利用枠の利点の薄さから凍結した（詳細は `202610_ClaudeCode連携/202610_ClaudeCode連携_凍結の経緯.md`）。
- 代わりに、ClaudeCodeで行われている「ファイルを探す → 中身を検索する → 読む → 答える」という動作を **ローカルLLM（Ollama）で再現する** ことを目標とする。
- ある程度の遅延と、ClaudeCodeとの性能差は受け入れる。

### 目標
- PKM（Obsidian）を **読み取り専用** で探索し、その内容を踏まえた会話・要約を行う。書き足し・編集・新規作成は行わない。
- Ollamaの利点である **モデルの自由度** を保つ。
- Thinking・画像入力（vision）・ツール呼び出しに対応していないモデルでも動作する。
- モデルの機能をアプリ側で把握・管理し、役割ごとのモデルの使い分けと、モデルに合わせた動作を行う。

### 前提環境
- **ターゲットユーザー層のGPU：VRAM 8GB** を基準とする（モデルサイズ・コンテキスト長・同時に載せるモデル数はこの範囲で成立させる）。
- 開発環境（2026-10-13 確認）
  - GPU：NVIDIA GeForce RTX 3070（VRAM 8GB）
  - Ollama 0.35.1
  - 現在の設定モデル：`gemma4:e2b-huggingface-q8`（4.6B / Q8_0 / 5.0GB）
    - ※ `gemma4:e4b` を使っていると記憶していたが、実際の設定と導入済みモデルはe2b系だった。
- 導入済みモデルの機能（Ollamaの `/api/show` が返す `capabilities` で確認）

| モデル | パラメータ / 量子化 | capabilities |
|---|---|---|
| `gemma4:e2b-huggingface-q8`（現在の設定） | 4.6B / Q8_0 | completion, tools, thinking |
| `gemma4:e2b` | 5.1B / Q4_K_M | completion, vision, audio, tools, thinking |
| `gemma3:4b` | 4.3B / Q4_K_M | completion, vision |
| `gemma3:12b` | 12.2B / Q4_K_M | completion, vision |
| `hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ1_M` | 34.7B / IQ1_M | completion, vision, tools, thinking |
| `embeddinggemma:latest` | 307M / BF16 | embedding |

- 同じGemma4 e2bでもタグによってvisionの有無が異なる。**機能の判定はモデル名やファミリーではなく、タグ単位で `capabilities` を見て行う。**
- 現在の `ai/AI_ollama.py` は `think`・`tools`・`options`（`num_ctx` 等）を指定していない。

### 基本方針

#### 1. ClaudeCodeの動作の分解と再現方法
| ClaudeCodeの要素 | ローカルでの再現 |
|---|---|
| 道具（Glob / Grep / Read） | `ai_tools` に読み取り専用のPKMツールを追加する |
| エージェントループ | 既存のReAct（`AI_main.react_planing`）を発展させる |
| ツール利用に長けたモデル | モデル選択と、索引・結果の切り詰めなどアプリ側の工夫で補う |

#### 2. PKMツール（読み取り専用）
| ツール | 役割 | 制限 |
|---|---|---|
| `pkm_glob` | パターンでファイル一覧を返す | 件数上限 |
| `pkm_grep` | キーワードで全文検索し、該当行と前後数行を返す | 件数・文字数上限 |
| `pkm_read` | ファイルを読む（行範囲指定可） | 1回の文字数上限 |
| `pkm_tree`（任意） | フォルダ構成の概要を返す | 深さ上限 |

- 書き込み系のツールは作らない（作らないことで読み取り専用を保証する）。
- パスがPKMのルートの外に出ないよう検査する（`..`・絶対パスを拒否）。除外フォルダを設定できるようにする。
- Obsidianのfrontmatter・タグ・`[[リンク]]` を手がかりとして返し、探索効率を上げる。
- ファイル名・タグ・更新日の索引をアプリ側で作り、最初からプロンプトに含めて「どこを見るか」の当たりを付けやすくする（上記「フォルダ名を使って探索」方針の延長）。

#### 3. モデルの機能に合わせた動作の切り替え
機能ごとに「あれば使い、なければ代わりの手段で動かす」。

| 機能 | ある場合 | ない場合 |
|---|---|---|
| thinking | `think` を有効にする（深さ指定ができるモデルは段階で指定） | 使わない。必要なら方針を考えるステップを1回足す |
| tools | ネイティブのツール呼び出し（`/api/chat` の `tools`） | `format` にJSON schemaを渡し、どのツールを呼ぶかをJSONで出させる（現行ReActをschemaで強制する形） |
| vision | 画像を添付する | 画像を送らない（または別モデルで画像を文章化して渡す） |

- Ollamaの `format`（schema指定）は生成時に出力形式を縛るため、モデルの機能に関係なく使える。これを全モデル共通の最終手段とする。
- 現行ReActの「自由文から正規表現でJSONを抜き出す」方式は、小さいモデルで崩れやすいため置き換える。

#### 4. モデルの管理と役割ごとの使い分け
- `/api/show` の `capabilities` を取得・キャッシュし、モデルごとの機能をアプリ側で把握する。
- 役割：会話（キャラクター応答）／探索（PKMツールのループ）／要約／埋め込み（将来のRAG用）。
- 役割ごとに「必要な機能」「あると望ましい機能」を定め、設定画面でのモデルの絞り込みや警告に使う。
- モデルごとの補足設定（使用するコンテキスト長、thinkingのon/offなど）は、自動判定の結果をユーザーが上書きできるようにする。

#### 5. VRAM 8GBでの制約
- 5GB級のモデルは2つ同時にVRAMへ載せられない。役割ごとに別モデルを割り当てると、切り替えのたびに再読み込み（数秒）が発生する。
  - → 既定は **1つのメインモデルを全役割で共用** とし、役割ごとの割り当ては任意とする。
- `num_ctx` を大きくするとKVキャッシュの分VRAMを消費し、溢れるとCPUに回されて大きく遅くなる。PKM探索では読み込んだ内容でコンテキストが膨らむため、`num_ctx` を設定できるようにし、ツール結果は要点だけ残して履歴を圧縮する。
- ループのステップ数上限、同じツール呼び出しの重複検出、上限到達時はそれまでの情報で答えさせる処理を入れる。

#### 6. 応答待ちへの対処
- ClaudeCode連携で検討したものと同様に、処理中であることをキャラクター側で示すUXを用意する（考え中の表情・一言など）。

### 次の一歩：実測の試作（`docs/tests/`）
導入済みの各モデルで以下を計測し、ステップ数上限・`num_ctx`・索引の作り込み具合などを決める材料にする。
- 読み込み時間・最初のトークンまでの時間・全体の応答時間
- thinkingのon/offによる差
- `num_ctx` を8k / 16kにしたときのVRAM使用量（`/api/ps` で確認）
- PKMの簡単な質問で、ツール呼び出し（ネイティブ / schema方式）がどれだけ成功するか
